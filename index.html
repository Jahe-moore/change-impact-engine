The problem, as a story

A supplier stops making one small sensor.

Picture a company that makes infusion pumps, the machines in a hospital that push medicine through an IV line at a set speed. Inside each pump is a small pressure sensor. It watches the IV line, so the pump can sound an alarm if the line gets blocked.

One morning the supplier says they are discontinuing that sensor. The company has to switch to a new one. Here is how that usually goes.

  1. Monday

    An engineer files a change request: "Replace the pressure sensor with one from a new supplier."

  2. Monday

    The coordinator emails the leads for electrical, firmware, mechanical and testing: "What does this affect on your side?"

  3. Tuesday to Thursday

    Each lead digs through their own tool and replies with a spreadsheet. Each one sees only their own piece.

  4. Next week

    Someone merges the answers, books a review meeting and starts chasing signatures.

  5. Months later

    An auditor asks why the blockage-alarm test was never run again on the new sensor. Nobody connected the two.

Why it's hard

The answer is split across three tools that don't talk to each other.

What the product must do

The requirements. "Check the IV line pressure at least 10 times a second." Owned by the systems engineers.

What the product is made of

The parts list. The sensor sits on the control board, and the control board sits inside the pump. Owned by the electrical and mechanical teams.

How each promise is proven

The tests. "Block the line and time how fast the alarm goes off." Owned by the test team.

The connections between those three live in people's heads and old spreadsheets. When one person forgets a connection, a test that should have been re-run gets skipped. In medical devices, the FDA expects every one of these reviews to be documented and traceable, so a missed connection is a real problem, not just a slow one.

How it works

Same sensor change. The system follows every connection for you.

Every connection is stored once, in one place: this part sits inside that board, this part is what makes that requirement true, this test checks that board. When something changes, the system walks those connections out from the change and collects everything it reaches.

Under the hood

Built the way a company would need it to work.

The demo is small, but each piece solves a problem a real company would hit. Each card names the technique once, then says what it does.

Three separate systems

Like the tools a company already has

Requirements, parts and tests each run as their own service with their own data. They only meet through the connections, the same way a real company's tools stay separate.

One table of connections

The map nobody had

Every "sits inside", "makes this true" and "is tested by" link is stored in one place. A single database query follows the links outward and records how far away each item is.

Outbox events

Changes never get lost

When a part is edited, the edit and a "this changed" message are saved together. Either both happen or neither does, so the system never misses a change or reacts to one that didn't happen.

Safe to retry

No double work after a crash

Each message is marked once it's handled. If it arrives twice, the second copy is skipped. If it keeps failing, it is set aside with the error after three tries instead of blocking everything else.

Approval routing

The right people, nobody extra

The owner of the changed part, the owner of every affected item, and configuration management. One rejection stops the change.

Tamper-evident log

A history you can trust

The database refuses edits and deletes on the log. Each entry is also sealed with a fingerprint of the one before it, so changing any old entry breaks the chain and the check catches it.

Tested, not just demoed

  • The sensor example returns exactly the five items above
  • A full change goes from filed to approved, and one rejection stops it
  • People who aren't approvers can't vote, and nobody votes twice
  • Editing a part opens a review by itself
  • A repeated message is not handled twice; a failing one is set aside after three tries
  • The log refuses edits, and the fingerprint check catches tampering

Tools

Python and FastAPI for the services. SQLite with recursive SQL for the connections. pytest for the 13 tests. Docker, set up to run as a locked-down, non-admin container.

Next on the list: PostgreSQL, a real message queue on AWS, sign-in for approvers, and an automated build that scans for security issues.

If a company wanted to try it

Start small and prove it first.

  1. Map one product line. Load the connections for one product only. Nothing changes about how anyone works yet.
  2. Run it side by side for a month. Let the change board work the normal way, and compare its answers with the engine's. Every difference is either a gap in the map or something the board missed.
  3. Turn on routing and the log. Once people trust the answers, let the engine send changes to approvers and keep the record.
